# 網站優化報告

> 日期：2026-08-06　範圍：住戶預約端 + 物業後台 + Firestore 安全規則 + Hosting 設定
> 驗證方式：實機瀏覽器測試（桌機 1280px／手機 375px）、production 環境端對端流程、安全規則滲透測試

---

## 一、修掉的真實 Bug（4 項）

### 1. 週計數的日期算錯一天（時區）⭐
`weekRangeOf()` 用 `toISOString()` 取日期，但那會把本地時間轉成 UTC。台灣是 UTC+8，本地午夜換算成 UTC 會退回**前一天**，導致「本週」的計數 key 標成週日而非週一。

**證據**：修正前後同一週產生的 key 不同——舊 `chess-room__11111__2026-08-02`（週日）、新 `chess-room__C棟-808__2026-08-03`（週一）。

改用本地時區的 `dateToStr()`，並抽成 `weekStartOf()`。舊格式的殘留計數文件已手動遷移。

### 2. 儀表板的設備警示會靜默失效 ⭐
後台儀表板原本用 `collectionGroup(equipment)` 查維修中的設備，這種查詢**需要額外建立索引**，而程式用 `try/catch` 把錯誤吞掉、回傳空陣列——結果是索引沒建時，畫面會顯示「目前沒有設備標記維修中」。

這是本系統最不能出錯的一項（設備故障管理是原始需求核心），卻會無聲地騙人。改成逐場地平行查詢（不需索引），錯誤一律顯示在畫面上。

### 3. 查詢碼用 `Math.random()` 產生
查詢碼等同於「取消這筆預約」的憑證。`Math.random()` 的輸出可被預測，不該用來產生任何具權限意義的字串。改用 `crypto.getRandomValues()`。

### 4. 時段標籤未跳脫，可破壞版面
`data-label="${t.label}"` 直接插入 HTML 屬性。物業若在時段名稱輸入含引號的字元會破壞 DOM 結構。已全面補上 `escapeHtml()`。

## 二、補上的產品缺口（3 項）

| 項目 | 修正前 | 修正後 |
|---|---|---|
| 住戶取消後的時段 | 卡住不放，要物業手動按「釋出時段」 | **自動釋出**，其他住戶立刻能訂 |
| 取消後的預約額度 | 不退還，住戶取消後仍被上限擋住且查不出原因 | **自動退還**（住戶端與後台取消皆是） |
| 查詢碼複製 | 只能自己看著打 | **一鍵複製**按鈕，剪貼簿被擋時自動退化成選取文字 |

「自動釋出時段」是靠安全規則實作的：規則會去 `get()` 對應的預約，**只有當該預約已是取消/拒絕狀態**時才允許釋出時段鎖。這樣既解除了限制，又不會讓任何人破壞別人的有效預約（已通過滲透測試驗證）。

### 其他強化
- 額度計數器規則從「任意整數」收緊為**只能 ±1 且不得為負**
- 查詢失敗訊息統一為「查無符合的預約」，不再區分「查詢碼錯」與「門牌不符」，避免被用來逐一試出哪些查詢碼有效
- 後台登入失敗不區分「帳號不存在」與「密碼錯誤」，避免被用來探測有效的管理員帳號
- 加上 `X-Content-Type-Options`、`X-Frame-Options`、`Referrer-Policy`、`Permissions-Policy` 標頭
- 後台頁面加 `noindex` 避免被搜尋引擎收錄

### ⚠️ 已知且刻意不修的限制

**同門牌的預約次數上限，在技術上無法真正強制。**

住戶可以把自己的額度計數器減 1 來取得額外配額。我評估後決定不堵這個洞，理由是：本系統採**免登入**設計，門牌號碼是住戶自己輸入的——想繞過上限，最簡單的方法是換一個門牌號碼再訂一次，根本不需要動計數器。

也就是說，在沒有住戶身分驗證的前提下，次數上限本質上只能是**提醒與摩擦**，不可能是真正的管制。把計數器鎖死卻擋不住換門牌，是白費的複雜度。

**若要讓上限真正有效，唯一的路是加入住戶身分驗證**（例如發放住戶帳號、或以門牌＋一次性密碼綁定）。這在需求訪談時已明確選擇不做。物業端的補償機制是「操作紀錄」——異常的密集預約仍然查得到。

## 四、無障礙（WCAG）

- 場地卡片與時段格從可點的 `<div>` 改成真正的 `<button>`，鍵盤 Tab／Enter 與螢幕報讀器可正常操作，並加上 `aria-pressed`
- 所有 `<label>` 補上 `for`，與輸入欄位正確關聯
- 分頁加上 `role="tablist"` / `role="tab"` / `aria-selected`
- 訊息區加 `aria-live`，狀態變化會被報讀出來
- 調整配色達 WCAG AA 以上：主色對白底 8.6:1、次要文字 7:1（原本的紅色 #dc2626 只有 4.0:1，未達標）
- `:focus-visible` 焦點框：鍵盤操作看得到、滑鼠點擊不干擾
- 支援 `prefers-reduced-motion`，會關閉動畫

## 五、行動裝置（電腦／手機／平板）

實測 375px 與 1280px，**頁面本身零水平溢出**。

- 表格統一包 `.table-wrap` 橫向捲動容器——六欄中文表格在手機上必然放不下，讓表格自己捲，頁面不會被撐破
- 觸控目標拉到 44px（原本分頁鈕 38px、後台連結僅 20px）
- 輸入欄位字級鎖 16px，避免 iOS Safari 自動放大整頁
- 輸入欄位補 `inputmode` / `autocomplete`，手機會跳出正確的鍵盤
- 查詢碼加 `user-select: all`，手機點一下就能全選

| 項目 | 做法 |

## 八、後續可考慮（本次未做）

- **深色模式**：社區住戶晚上用手機訂位的比例應該不低
- **住戶身分驗證**：唯一能讓次數上限真正生效的方法（見第三節）
- **預約成功通知**：目前只有查詢碼，可考慮加 Email 或 LINE 通知
- **場地照片**：目前只有文字，加圖片能降低訂錯場地的機率
- **設備狀態去正規化**：把「場地是否被必要設備擋住」寫進場地文件，可把首頁查詢從 7 次降到 1 次。目前 6 個場地是平行查詢，延遲影響不大，但場地數量成長後值得做
